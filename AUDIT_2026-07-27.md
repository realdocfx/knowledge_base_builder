# Knowledge-Base-Builder 0.5.0 — Technical Audit

**Date** 2026-07-27 · **Scope** `C:\Users\USER\Developer\knowledge_base_builder` @ `5757717` (7 files dirty)
**Corpus** 7,292 LOC Python (14 modules), 250 LOC Rust (Tauri 1.5), 1,610 LOC tests, 3 CI workflows, 1 SBOM
**Method** Full read of every source module; static analysis (pyflakes); partial test execution under CPython 3.10; empirical verification of filesystem-detection, hash-API and state-machine claims in a Linux sandbox.
**Not covered** The deployed stick at `D:\` — filesystem roots cannot be mounted. Deployed-artifact verification (binary provenance, `.kb_env` integrity, actual on-disk state) remains outstanding and is a prerequisite to any acceptance test.

---

## 1. Verdict

The system is a competent single-operator tool with a genuinely good idea at its core — a self-contained ZIM/Archive.org acquisition and reading stack that survives on removable media. It is **not** procurable in its present state by any of the four target authorities. The blocking issues are not cosmetic.

Three findings are disqualifying on their own:

1. **`cli.py:467` — `datetime` is undefined.** Every `kb-builder pull` that completes successfully then raises `NameError`, is swallowed by the outer handler, prints `Critical Sync Failure`, and exits 1. The primary acquisition command has never returned success. Confirmed by pyflakes; no test covers `pull`.
2. **FAT32 splitting is inoperative on Linux and macOS.** `os_utils.get_fs_type` parses `df -T`, which reports `vfat`/`msdos` — never the literal `FAT32` that `ZimBucket._detect_fat32_mode` tests for. On macOS, `df -T` takes a *type filter*, not a path, so the parse is meaningless. The stated OS-independence of the removable-media core does not exist.
3. **The `/files`, `/read`, `/epubres` and `/wiki` data plane is unauthenticated,** and serves attacker-supplied HTML/SVG/EPUB same-origin with the control plane. Combined with the unescaped `r.identifier` interpolation at `web.py:1754`, remote Archive.org metadata reaches the operator's console as executable script with an authenticated session cookie in scope.

The documentation asserts guarantees the code does not implement — "mathematically perfect atomic write", "$O(1)$ lookup", "air-gapped", "MIL-SPEC COMPLIANCE: uses requirements.txt with SHA-256 hashes". Each of these is falsified below. For procurement this is worse than the defects themselves: an evaluator who checks one claim and finds it hollow discounts the entire evidence package.

**Assessed maturity:** TRL 4–5 (validated in a representative environment by its author). Procurement-grade is TRL 7–8 plus an evidence chain. The gap is roughly 6–9 months of disciplined work, most of it not feature work.

### 2.1 What is sound

- **The bucket/engine abstraction** (`base.py`) is a clean two-axis ABC. Adding a source or a target is a contained change.
- **Lazy imports** (`__init__.py` PEP 562, `_make_engine`, `get_engine`) are correct and well-motivated — importing `internetarchive` off USB costs seconds. This is guarded by `tests/test_import_performance.py`, one of the few tests that asserts behaviour rather than the presence of a CSS token.
- **ZIM integrity verification** (`zim.py:456–520`) implements the actual container spec: MD5 over the payload excluding the trailing 16-byte digest, plus magic-number check on the first slice. The `usedforsecurity=False` treatment for FIPS hosts is the right call and correctly reasoned in the comment at `zim.py:3–9`.
- **Split geometry is deterministic.** `FAT32_CHUNK_LIMIT` is a fixed constant, so slice *k* always covers the same byte range across runs. This is what makes the resume logic in `_get_split_progress` safe despite never truncating stale slices.
- **The control-plane token design** (`web.py:63–96`) is correct in kind: `secrets.token_urlsafe(32)`, `compare_digest`, one-shot `?t=` → HttpOnly `SameSite=Strict` cookie. The reasoning in the comment — that loopback is not a trust boundary — is right, and rarer than it should be.
- **Ergonomic instincts are real.** Determinate progress on every long operation, elapsed counters, named recovery actions on failure, no dead "Initializing…" states, keyboard-only navigation, and a night optic that *declares* colours rather than inverting the document (`WIKI_STEALTH_INJECT`, `web.py:1942`). The commit that replaced `invert()` with declared phosphor colours is a genuinely correct piece of human-factors engineering.

### 2.2 Structural faults

**Duplicated state machine.** `UsbBucket` and `ZimBucket` carry ~150 identical lines: `get_state`, `update_state`, `_flush_state_to_disk`, `mark_item_completed`, `mark_item_failed`, `is_item_completed`, `get_stats`, `_format_bytes`. They have already diverged: `usb.py:98–103` closes the directory fd in a `finally` block; `zim.py:113–114` leaks it on fsync failure. `_format_bytes` exists four times (`base.py:53`, `usb.py:173`, `zim.py:620`, `presentation.py:15`) with two different rounding conventions. Bug fixes land in one copy.

**Two parallel orchestrators.** `wiki_orchestrator.py` (493 LOC) is an `argparse` program with its own state file (`.kiwix_processed.json`), its own non-atomic persistence (`_save_processed` uses bare `write_text`), and its own capacity logic. It is not in `[project.scripts]`, does not use `BaseBucket`, and is not tested. It is the only module that implements FAT32-aware staging — and it does so with the same broken `get_fs_type` check.

**Presentation layer bypassed.** `presentation.serve_bucket:141` calls `webbrowser.open` directly instead of `os_utils.open_browser`, and `launch_kiwix_server:112` omits `--address 127.0.0.1` — so the `kb-builder serve` path binds kiwix-serve to **all interfaces**, unlike the portal path (`web.py:363`) which does bind loopback. Same function, two files, one hardened, one not.

**`web.py` is 2,574 lines**, of which ~1,400 are inline HTML/CSS/JS in string constants. The dashboard, three themed page templates, a Markdown renderer, an EPUB spine parser and the routing table share one module. Any front-end change requires editing Python string literals with no template engine, no escaping discipline, and no linting.

## 4. Removable-media subsystem — detailed

The FAT32 story is the product's differentiator and it is the least finished part of it.

**What works.** `FAT32_CHUNK_LIMIT = 3900 MiB` is a correct and conservative bound against FAT32's 4 GiB − 1 B file ceiling. The `.zimaa`/`.zimab` suffix scheme matches Kiwix conventions. A single MD5 is carried continuously across all slices and compared against the digest in the last slice's trailer, with the magic number checked on the first — that is the right verification, done correctly. Slice boundaries are deterministic, which makes resume safe.

**What does not.**

- Detection is string-matched against `"FAT32"` — a Windows `GetVolumeInformationA` output. POSIX never produces it (D2).
- `get_fs_type(target_file)` is called on a path that **does not yet exist**. On Windows `Path.anchor` still yields the drive, so it happens to work; on POSIX `df -T <nonexistent>` fails and returns `""`. The Windows correctness is accidental.
- No FAT32 handling at all in the Archive.org path (D37), where remote filenames additionally violate FAT32/NTFS naming rules.
- FAT32's 32 KB cluster size is never accounted for. On a library of many small Archive.org files, slack space is 15–40 % of capacity. `check_capacity` compares raw bytes to raw free space — and is not called anyway (D36).
- exFAT is not detected or handled, despite being the correct filesystem for this use case (no 4 GiB limit, universally mounted, no journal). The product forces the operator onto FAT32's constraint and then only half-solves it.
- `--with-portable-rust` correctly documents that FAT32 lacks the links rustup needs — good — but this is the only place where the FAT32 constraint is honestly surfaced to the operator.
- Atomic-rename durability does not exist on FAT32 (D11), and the directory-fsync barrier is skipped on Windows.

**Consequence for the mission profile.** A stick formatted FAT32 for universal mountability, filled on Windows, then read on a Linux host, then re-provisioned on that Linux host, produces: correct reads, broken re-provisioning (D26), broken splitting (D2), and a clone that silently drops files (D12). The cross-platform round trip — which is the entire point of a stick — is not achievable today.

## 6. Security posture

### 6.1 Network exposure

Loopback binding is correct in the portal path and in the launcher. Three holes: `presentation.launch_kiwix_server` omits `--address`, exposing kiwix on all interfaces from `kb-builder serve` (§2.2); `portal --host 0.0.0.0` is accepted without objection (D19); and the data plane is unauthenticated regardless of bind address (D4).

There is no TLS anywhere — defensible for loopback, indefensible the moment `--host` is used. There is no rate limiting, no request logging suitable for audit, no session expiry, no per-operation authorisation, and no separation between "read the library" and "clone the drive to an arbitrary path".

### 6.2 Content trust

The system's threat model treats the *operator's browser* as trusted and everything else as irrelevant. The actual threat is inverted: this tool exists to ingest content from Archive.org and Kiwix — adversary-reachable sources — onto an operator's machine, and then render it. Every ingested artefact is untrusted input. Today it is rendered same-origin with the control plane (D6), its metadata is interpolated into script context (D5), its XML is parsed with a vulnerable parser (D21), and its archives are decompressed without bounds (D22).

The correct architecture is a hard origin split: content served from a distinct port/origin with `Content-Security-Policy: sandbox`, `Content-Disposition: attachment` for anything not explicitly whitelisted, and no ambient credential in scope. This is the single highest-value change in the entire report.

### 6.3 Cryptography

- SHA-256 for provisioning assets: correct, FIPS 140-3 approved.
- MD5 for ZIM: mandated by the container format, correctly marked `usedforsecurity=False`, correctly documented. This is defensible to an evaluator **if** it is written down as a formal deviation with the format citation. Right now the justification lives in a source comment.
- No cryptographic signature verification anywhere. Hashes pinned in a Python literal are integrity checks against a value the same repository controls; they are not provenance. There is no GPG/Sigstore/Authenticode verification of kiwix-tools, of python-build-standalone, of the Xapian wheel, or of the launcher.
- `rustup-init.exe` is fetched and executed with nothing (D7).
- No FIPS mode enforcement, no crypto-module inventory, no key management (the only secret is an ephemeral token in a world-readable temp file).

### 6.4 Supply chain

The repository *presents* a supply-chain posture — pinned hashes, an SBOM, a `--local-bundle` air-gap flag, `MIL-SPEC COMPLIANCE` comments. Under inspection: the hash-pinned requirements file is never used (D8), the air-gap flag does not cover the dependency tree (D9), the SBOM is malformed and licence-free (D32), the wheel pipeline is a no-op (D30), the wheel *build* verifies nothing (D31), the launcher is unsigned (D10), and the release path silently downgrades from OIDC trusted publishing to a static token (D29).

This is the finding that will end a procurement conversation fastest, because it is the one an evaluator can check in ten minutes without reading any code.

## 7. Mathematics and state model

The docstrings make three quantitative claims. All three are false as written.

**"$O(1)$ in-memory update followed by mathematically perfect atomic disk write"** (`usb.py:113`). The operation is: read the entire state file → `json.loads` → mutate → `json.dumps` → `fsync` → `os.replace`. Cost is O(S) in serialised state size per call, and S grows linearly with completed items. Over an N-item sync the aggregate is Θ(N²) bytes of I/O.

**"$O(1)$ lookup against the parsed application state"** (`usb.py:141`). `is_item_completed` re-reads and re-parses the file on every call, then performs `identifier in list` — a linear scan. Called once per item in `_process_item`, this is Θ(N²) comparisons on top of Θ(N²) I/O.

**"mathematically perfect atomic state write"** (`usb.py:81`, `zim.py:96`). Atomicity of `os.replace` is a property of the filesystem, not of the call. FAT32 provides none, and the directory-fsync fallback is compiled out on Windows (D11).

The fix is small and standard: hold state in memory for the process lifetime, use a `set` for `completed_items`, write a per-item append-only journal (one line, one `fsync`) rather than rewriting the whole document, and compact to the JSON snapshot on clean shutdown. That converts Θ(N²) to Θ(N) and makes crash recovery a replay rather than a hope.

The **hash-window arithmetic** in `_update_hash` (`zim.py:597`) is correct for `total_size > 16` and degenerate for `total_size == 0` (D3). The three-way branch cleanly handles a chunk straddling the checksum boundary — good code, one missing precondition.

The **queue prioritisation** in `wiki_orchestrator.py` (Jaccard-alternating nearest/furthest topic selection, `ProximityScorer`) is an interesting heuristic for maximising topical coverage under a size budget. It is also `O(n²)` in a `while remaining:` loop with `max()` and `remove()` per iteration, unvalidated, untested, and driven by hand-written keyword lists that make `VitalArticlesIndex` a lookup table wearing the name of a Wikipedia project it does not actually read.

## 9. Ergonomics

Assessed against the MIL-STD-1472H clauses the code itself cites.

**Sound.** Determinate progress with elapsed counters on every operation exceeding 10 s (5.17). Failure states name a recovery action rather than an error code (5.17.10.7). No terminal "Initializing…" — every panel retries and says so. Keyboard-only navigation with `/`, `Esc`, `1`–`6`, `Alt+N`. Single source of truth for navigation (`NAV_SECTIONS`) with a documented rationale for *not* duplicating it in the masthead. The night optic declares colours in the 520–555 nm band rather than inverting the document, with a stated contrast figure (~11.5:1 against a 10:1 target) — this is the correct method and the commit history shows it replaced an incorrect `invert()` approach.

**Gaps against the same standard.** No accessibility conformance work: contrast is specified for the stealth optic only, not for the standard Mosaic optic where `--ink-soft:#404040` on `--panel:#d0d0d0` is ~5.9:1 and `.fmeta` at 0.78 rem falls below comfortable minima. No `aria-live` on the status regions that update asynchronously, so a screen reader never announces "LINK DOWN" or clone progress. No focus management when the `#viewport` overlay opens — focus stays behind the overlay and `Tab` walks the hidden document. `alert()` for job confirmation (`web.py:1848`) is a modal that cannot be styled, cannot be read by the stealth optic, and blocks the event loop. No i18n despite a `.lang-btn` class named for it. Colour is the sole channel for state in the metric tiles (5.2.2.1 requires redundant coding).

**Operationally significant.** The clone completion message reports success with a parenthetical skip count (D12). Under MIL-STD-1472H's own principle that a failure must be unambiguous, "Duplicate complete (1 file(s) skipped)" for a clone that dropped the 90 GB Wikipedia archive is a mis-annunciation, not a warning.

### 10.2 Five Eyes (US-led)

**Frameworks:** NIST SP 800-218 (SSDF), NIST SP 800-53 Rev 5 / 800-171 Rev 3, EO 14028 SBOM attestation, DISA STIG / SRG, FIPS 140-3, CMMC L2 for the supplier, Section 508 / WCAG 2.1 AA.

**Specific gaps beyond §10.1:**
- **AU family (Audit)** — nothing. No audit log of who downloaded what, when, to which target. `logging` output goes to stdout and `portal.out.log`. AU-2, AU-3, AU-9, AU-12 all unmet. For an OSINT collection tool this is the single most conspicuous absence: collection provenance is the product.
- **AC family** — no roles, no least privilege, no separation between read and administrative operations. AC-3, AC-6 unmet.
- **IA family** — one shared bearer token, no identity, no MFA, no credential lifecycle. IA-2, IA-5 unmet.
- **SC-8 / SC-13** — no transport protection; crypto module not enumerated.
- **SI-7** — software integrity: the atomic-write claim (D11) and the clone verification gap (D12) are directly in scope.
- **SSDF PW.4 / PW.7 / PS.2** — no third-party component review, no code review evidence, no signed releases.
- **Section 508** — §9 gaps are disqualifying for a US federal buy without a credible VPAT.
- **STIG** — an application STIG checklist does not exist for this product and would need authoring; the CSP `unsafe-inline`/`unsafe-eval` and the unauthenticated endpoints would fail generic Application Security & Development STIG findings on first pass.

**Blocking severity:** highest of the four. Do not approach a US programme office before the audit-log subsystem exists.

### 10.3 France (SGDSN / ANSSI)

**Frameworks:** ANSSI CSPN (*Certification de Sécurité de Premier Niveau*) as the realistic first target; Common Criteria EAL2+ for anything above *Diffusion Restreinte*; RGS for cryptographic mechanisms; RGAA 4.1 for accessibility; *Référentiel d'exigences* for *qualification élémentaire*.

**Specific gaps:**
- **CSPN requires a *cible de sécurité*** — a formal security target defining assets, threat agents, assumptions and security functions. None exists. This is the first deliverable, before any code change, and writing it will itself expose the D4/D6 architecture problem.
- **RGS Annexe B1** — MD5 is *déconseillé*. The ZIM-format justification is sound and ANSSI will accept a documented *dérogation* for a format-mandated integrity digest, but only as a written, referenced deviation with a stated residual-risk analysis. Get this on paper.
- **Qualification requires French or EU sovereignty considerations** on the toolchain. `python-build-standalone` (Astral, US), NuGet WebView2 (Microsoft, US), `win.rustup.rs` (US), GitHub Actions (US) are all in the build path. For *DR* and above, expect questions about build-chain jurisdiction. A mirrored, self-hosted provisioning bundle answers this — and is the same work as fixing D9.
- **RGAA 4.1** — the §9 accessibility gaps map directly; RGAA is stricter than WCAG AA on some criteria.
- **CSPN evaluation is time-boxed** (typically 25–35 person-days at a CESTI). A codebase with D28 (no CI) and D43 (untestable from clean clone) will consume that budget on environment setup.

**Assessment:** CSPN is achievable within ~9 months *if* §10.1 is closed and a *cible de sécurité* is written first. The night-optic and MIL-STD-1472H work is genuine differentiation in a French context — ANSSI evaluators respond well to demonstrated human-factors rigour.

### 10.4 Türkiye (MİT / SSB)

**Frameworks:** TSE / TS ISO/IEC 15408 (Common Criteria via TSE-CCCS), *Bilgi ve İletişim Güvenliği Rehberi* (Presidential Digital Transformation Office ICT Security Guide), KVKK for any personal data, SSB *yerlilik* (domestic-content) scoring.

**Specific gaps:**
- **Localisation.** Zero i18n infrastructure — every string is a hardcoded English literal inside Python source or inline JS. Turkish UI is a prerequisite, not a nice-to-have, and retrofitting it into 1,400 lines of inline HTML string constants is expensive. Extract to a resource file now.
- **Turkish locale correctness.** The dotted/dotless İ/ı casing rule breaks naive `.lower()`/`.upper()`. `cli.py:133` (`source.lower()`), `archive_index.py:116` (`.upper()`), `wiki_orchestrator.py:67` (`.lower()`) and the format-matching in `engines/archive.py:65` will misbehave under a Turkish locale. Use `casefold()` or explicit invariant casing.
- **Turkish tokenisation.** `tokenize='unicode61'` (`archive_index.py:258`) has no Turkish stemming; agglutinative morphology means recall on Turkish content will be poor. `unicode61 remove_diacritics 2` plus a Turkish stemmer or trigram fallback is needed.
- **BİLGEM / TSE-CCCS certification** needs the same Protection Profile / Security Target work as CSPN.
- **Domestic-content scoring** disfavours a stack whose entire provisioning chain resolves to US-hosted artefacts. A self-hosted mirror is worth real points here — again the same work as D9.

**Assessment:** the localisation and Turkish-language-processing work is a distinct 2–3 month workstream that does not overlap with the security remediation. Start it in parallel.

### 10.5 NATO ("NATO-green" / NATO UNCLASSIFIED–RESTRICTED)

**Frameworks:** AC/35-D/2004 & D/2005 (INFOSEC management and technical directives), NIAPC listing, STANAG 4774/4778 (confidentiality metadata labelling and binding), NCIA acquisition, AQAP 2110/2210 (quality assurance for software), NATO Interoperability Standards and Profiles (NISP).

**Specific gaps:**
- **STANAG 4774/4778 labelling is the defining gap.** A NATO knowledge system must bind a confidentiality label to every information object and enforce it on display, export and transfer. This system has no concept of classification at any layer: not in `sync_state.json`, not in the FTS5 schema, not on `/files`, not on export, not on clone. Adding it is not a feature — it is a schema and data-model change across `BaseBucket`, `ArchiveIndex`, every rendering path, and the clone function. **Budget this as the largest single item.**
- **Releasability / caveat handling** — no mechanism for REL TO markings, which is precisely what a multi-national OSINT product needs.
- **Cross-domain transfer.** The stick *is* a transfer mechanism between security domains. Today it moves unlabelled, unverified, unlogged content across an air gap. Any NATO accreditor will treat `cloning.py` as a cross-domain solution component and hold it to that standard: verified copy with digest manifest (D12), immutable transfer log, and label enforcement. It currently has none of the three.
- **AQAP 2110** requires a documented quality management system: configuration management, defect tracking, review records, verification records. `git log` with 27 commits and no CI is not a QMS.
- **NIAPC listing** requires an evaluated product; see CC path above.
- **Media sanitisation** — no secure-erase path for a stick being returned or re-tasked.

**Assessment:** NATO-green is the longest path (12–18 months) because of labelling, but it is also the path where this product's concept is strongest — a labelled, verifiable, offline knowledge stick with a night-compliant reader is a real capability gap in NATO deployments.

## 11. Remediation sequence

Ordered by (blocking severity × cost of deferral), not by ease.

### Phase 0 — one week, before anything else
1. Fix D1 (`import datetime`). Add a `pull` integration test against a local HTTP fixture.
2. Add `.github/workflows/ci.yml`: pytest on Windows + Linux + macOS × Python 3.11–3.13, plus mypy, ruff, and `pip-audit`. Add `pythonpath = src` to `pytest.ini`. Make the pre-commit hook redundant.
3. Fix D33 — either raise `requires-python` to `>=3.9` or guard the `usedforsecurity` call. Do not ship a false support matrix.
4. Fix D3 — reject `total_size <= 16`, and assert `temp_file.stat().st_size == total_size` before verification. This defect destroys completed multi-hour transfers.
5. Fix D7 — pin or remove the rustup path. An unverified downloaded executable is indefensible in any of the four contexts.

### Phase 1 — one month, security architecture
6. **Split the origin.** Serve `/files`, `/read`, `/epubres`, `/wiki` from a separate port with `Content-Security-Policy: sandbox`, no ambient cookie, and `Content-Disposition: attachment` for non-whitelisted types. Closes D4, D5, D6, D24 structurally rather than by escaping.
7. Remove `unsafe-inline`/`unsafe-eval` from both CSPs; move inline handlers to attached listeners; add `frame-ancestors 'none'`. (D20)
8. Escape all interpolation in the generated JS/HTML; adopt a template engine or move the front end to static files. (D5, D24)
9. `defusedxml` everywhere; bound all `zipfile.read` by declared size and ratio. (D21, D22)
10. Constrain `/api/download` `target` and `/api/clone` `dst` to a whitelist of mounted removable volumes. (D23)
11. Token file with `0600` on POSIX and a per-run random name; strip `Cookie`/`Authorization` in the kiwix proxy. (D18, D25)
12. Refuse non-loopback `--host` unless an explicit `--i-understand-this-is-exposed` flag is passed **and** the data plane is authenticated. (D19)

### Phase 2 — two months, removable-media correctness
13. Rewrite `get_fs_type`: `GetVolumeInformationW` on Windows; `statfs`/`f_type` or `/proc/mounts` on Linux; `statfs.f_fstypename` on macOS. Normalise `vfat`/`msdos`/`FAT32` → `FAT32`, add `exFAT`, `NTFS`, `ext4`, `APFS`. Unit-test each mapping. (D2)
14. Extend split-writing and filename sanitisation to the Archive.org path. Add exFAT as the recommended format with a documented rationale. (D37)
15. Replace the JSON-rewrite state layer with an append-only journal + periodic compaction; `set` for membership. Delete the false complexity annotations. (D34, D35)
16. Make `os.replace` durability explicit: document that FAT32 provides no atomicity, add a write-ahead marker so a torn rename is detectable on next open, and fsync the directory on Windows via `FlushFileBuffers` on a directory handle. Replace "mathematically perfect" with a precise statement of what is and is not guaranteed per filesystem. (D11)
17. Verified clone: pre-flight destination capacity and per-file size checks, digest manifest written to the target, `fsync` per file, and `state="error"` on any skip. (D12) Checkpoint the SQLite WAL before copying. (D13)
18. Fix POSIX provisioning (D26) and cross-target provisioning (D27), or remove the claims and the `--target-os` flag.

### Phase 3 — three months, procurement evidence
19. **Audit logging subsystem.** Append-only, tamper-evident (hash-chained), covering acquisition, read, export, clone and configuration change, with operator identity. This is the prerequisite for every one of the four authorities and it does not exist in any form.
20. Regenerate the SBOM: CycloneDX 1.6, `metadata.component`, full `dependencies` graph, licence for every component, correct hashes. Attach to releases, sign with cosign, publish SLSA provenance via `actions/attest-build-provenance`. (D32)
21. Actually use `requirements.txt --require-hashes`; make `--local-bundle` cover the full dependency closure including wheels; drop the `PYPI_API_TOKEN` and use OIDC alone. (D8, D9, D29)
22. Fix the Xapian wheel pipeline (D30) and add checksum verification to its build (D31). Pin all `actions/*` to commit SHAs.
23. Sign the launcher: Authenticode with an EV certificate on Windows. Configure `tauri.bundle.windows` properly. Migrate to Tauri 2.x. (D10, D41)
24. Rewrite `SECURITY.md` to ISO/IEC 29147 with a real contact, PGP key and response SLA. (D42)
25. Commission an independent penetration test and publish the remediation record.

### Phase 4 — parallel workstreams, per authority
- **FR:** author the CSPN *cible de sécurité* — start now, it is cheap and it drives the architecture. Formalise the MD5 deviation against RGS B1. RGAA 4.1 remediation.
- **TR:** extract all strings to resource files, add Turkish UI, fix locale-sensitive casing, add Turkish tokenisation/stemming to FTS5. Stand up a self-hosted provisioning mirror.
- **NATO:** design STANAG 4774/4778 label binding into `BaseBucket` and the FTS5 schema before Phase 2 lands, so the state-layer rewrite carries it. Treat `cloning.py` as a cross-domain component and specify it accordingly.
- **5I:** Section 508 / WCAG 2.1 AA remediation with a VPAT. NIST SP 800-53 control mapping document. Application STIG checklist.

## 12. What to keep

Remediation should not become a rewrite. These are correct and should survive intact: the `BaseEngine`/`BaseBucket` abstraction; the lazy-import discipline and its performance tests; the ZIM verification arithmetic in `_update_hash`/`_verify_and_finalize`; the deterministic split geometry; the control-plane token *design* (its transport needs fixing, not its concept); the declared-colour night optic and the reasoning behind rejecting `invert()`; the determinate-progress and no-dead-state discipline throughout the UI; and the habit — visible in the comments and commit messages — of recording *why* a thing was done and what failed before it. That last one is the most valuable asset in the repository and the reason this codebase is worth hardening rather than replacing.
